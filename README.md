# ESP32 CAN heat exchanger logger (Hoval TopTronic E)

ESPHome firmware for an ESP32 + SN65HVD230 CAN board that supervises a heat exchanger
controlled by a **Hoval TopTronic E** controller over its CAN bus. Home Assistant logs the
data and adds statistics, KPIs and alerts.

```
Hoval TopTronic E ──CAN 50k──> ESP32 (ESPHome)                          ──WiFi/API──> Home Assistant
  (FW / WEZ / …)               • toptronic component: polls datapoints          • history + long-term statistics
  + heat meter                 • heat exchanger signals: temps, power,          • energy per day/week/month/year
                                 energy (heat meter), flow, ΔT                  • effectiveness, LMTD, UA (fouling)
                               • bus health, protocol debug switches            • dashboard, alerts
```

> **Status:** build chain, firmware and HA side are complete and compile. The **signal map**
> (which Hoval datapoints feed the logger's signals) holds defaults for a district heating
> station (`FW`) and must be verified on the real installation:
> [docs/hoval-toptronic.md](docs/hoval-toptronic.md).

## Build chain

Requirements: Linux/macOS, Python ≥ 3.11, `make`, `git`, `openssl`. ESPHome is installed into
`.venv` in a pinned version ([requirements.txt](requirements.txt)). The ESP-IDF toolchain is
downloaded on the first compile (≈ 1 GB, a few minutes).

```bash
make setup      # .venv with pinned ESPHome + esphome/secrets.yaml (random API key)
$EDITOR esphome/secrets.yaml   # WiFi credentials
make check      # yamllint + HA consistency + vendored-component check + config validation (both variants)
make compile    # firmware -> build/heat-exchanger-logger.{factory,ota}.bin
make upload DEVICE=/dev/ttyUSB0   # first flash over USB
make upload                       # later: OTA over WiFi
make logs       # live log  (make capture: same, saved to captures/)
make help       # all targets
```

The ESPHome web dashboard is also available (`make dashboard` → http://localhost:6052), as is the
HA ESPHome add-on: copy the `esphome/` folder into its config directory.

**CI** ([.github/workflows/ci.yml](.github/workflows/ci.yml)): on every push/PR it runs lint and
config validation, then a firmware build uploaded as an artifact. Tags `v*` attach the binaries
to a GitHub release.

## Commissioning, step by step

1. Hardware: check [docs/hardware.md](docs/hardware.md), especially the termination jumper and the power supply notes.
2. Confirm the Hoval device type/address, then `make setup`, fill in WiFi, and flash the discovery
   firmware: `make upload DEVICE=/dev/ttyUSB0 CONFIG=heat-exchanger-logger-discovery.yaml`.
3. Add the device in HA (API key from `esphome/secrets.yaml`).
4. Find the datapoints and fill in the signal map ([docs/hoval-toptronic.md](docs/hoval-toptronic.md)),
   then flash the production firmware: `make upload`.
5. Add `Heat energy` to HA's **Energy panel**, and install the HA package + dashboard
   ([homeassistant/README.md](homeassistant/README.md)).
6. After a day of normal operation, set the UA reference for fouling detection.

## Design decisions

- **Reuse the maintained `toptronic` component**, don't reimplement the protocol (multi-frame
  reassembly, CRC, polling). It is vendored at a pinned commit plus a small, documented patch that
  CI verifies, so upstream changes never land unreviewed. Alternatives reviewed (HoxPi,
  hoval-exporter, Hoval-GW, CAN-Gateway) are not ESPHome-based. The ESPHome core PR for this
  component is still a draft.
- **Read-only production firmware.** It polls only the signal map's datapoints (`presets: false`):
  no writable entities, minimal bus load. The discovery variant shows everything, for commissioning only.
- **Stable logger signals.** HA KPIs and dashboards use the logger's own entity names (Heat power,
  Primary inlet temperature, …). Switching device type or meter index only changes the signal map.
- **Energy story in HA's built-in Energy panel** (as a "gas" source in kWh, HA's standard slot for
  heat meters). The custom dashboard covers live values, condition KPIs and diagnostics.
- **Power and energy from the Hoval heat meter**: a calibrated M-bus meter, better than
  integrating flow × ΔT. Energy is exposed in kWh as `total_increasing`, so it works with the HA
  Energy dashboard. Zero and decreasing readings are filtered so glitches can't be counted as
  meter resets.
- **Missing data is shown as missing:** a signal not refreshed for 300 s becomes `unknown`.
- **Security:** API and OTA are encrypted with the same random key. The web server has no
  firmware upload. Fallback AP with password.
